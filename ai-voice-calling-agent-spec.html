01 / PRODUCT DEFINITION

What are we building?

A phone- and browser-accessible agent capable of natural spoken conversations, permitted tool execution, and human escalation. The three variants share conversational requirements but have dramatically different engineering scope, costs, and ownership boundaries.

A.FASTEST MVP

Hosted voice agent

Own the user experience and business workflows; delegate speech inference and media infrastructure to managed providers.

Read specification ↗
B.MODEL CONTROL

Self-hosted voice AI

Operate speech, language, and voice generation on your GPU infrastructure with explicit model and latency constraints.

Read specification ↗
C.SAAS PLATFORM

Voice infrastructure

Deliver reusable multi-tenant agent, telephony, billing, routing, observability, and deployment primitives to third parties.

Read specification ↗
!
Recommended sequence: A → selected B components → C only with validated demand

These are three different business bets, not three phases that must all be completed. Approach C creates an infrastructure/SaaS business with substantially greater operational scope. Starting there is an expensive assumption unless multiple customers specifically need your own platform.

02 / VOICE MODEL LANDSCAPE

Product voice ≠ developer API

Models that power ChatGPT Voice are not automatically model identifiers you can deploy with an API key. Keep consumer product models, documented developer API models, and open-weights research models in separate categories.

CHATGPT PRODUCTOCT 2026

GPT-Live-1.1

Full-duplex voice model used in eligible paid ChatGPT Voice experiences. Natural overlapping speech, turn handling, pacing, and interruptions. This name is not presented here as a public developer API model ID.

CHATGPT PRODUCTOCT 2026

GPT-Live-1.1 Quip

Smaller GPT-Live variant used on ChatGPT Free and Go experiences, subject to account limits. Do not treat a ChatGPT Free/Go/Plus subscription as an API entitlement.

DEVELOPER APIDOCUMENTED

gpt-live-1

Developer-facing full-duplex voice model with delegation to a backend agent. Documented API session price: US$0.05/min, billed per second; backend model/tool fees are additional. Verify current availability and quotas in your API organization.

DEVELOPER APIDOCUMENTED

gpt-realtime-2.1

Audio-in/audio-out developer model offering reasoning and tool use over realtime sessions. Different product behavior and pricing model than GPT-Live. A mini variant is also listed in API documentation.

i
Engineering rule: configure models by exact API ID, not marketing name

This specification uses the exact documented API names gpt-live-1 and gpt-realtime-2.1 as references. Model availability, pricing, quotas and endpoints are not interchangeable. GPT-Live-1.1/Quip are useful architectural inspiration, not guaranteed API deployment options.

What creates the “human” feeling?

01 / TRANSPORT

Low-jitter frames

WebRTC, jitter buffers, RTP timing, echo handling and efficient frame scheduling.

02 / INFERENCE

Streaming speech

Generate audio before a complete message is finished; avoid sequential blocking.

03 / CONVERSATION

Barge-in & overlap

Handle pauses, acknowledgements, false interruptions and speaker transitions.

04 / TOOLS

Async delegation

Continue dialogue while slow database, tool or reasoning operations complete.

Design constraint: never place synchronous database calls on an audio frame delivery path.

Telephony / SIP

Connect telephone numbers, create and terminate calls, bridge narrow-band telephony audio to WebRTC rooms, transfer to humans.

Media / WebRTC

Secure realtime streams (RTP/SRTP), SDP negotiation, Opus/PCM codecs, jitter buffering, packet loss, audio pacing.

Agent runtime

Dialogue orchestration, backchannels, interruptions, tool deadlines, conversation state, audio output cancellation.

Inference adapters

Pluggable realtime model, or STT → text LLM → TTS. Provider selection must be per-tenant configurable in C.

State & persistence

Postgres for authoritative calls/events; Redis for ephemeral presence, idempotency guards, scheduling and rate limits.

Safety & observability

Consent, disclosures, audit trail, recording control, metrics, latency spans, prompt/tool versioning, human handoff.

05 / STRATEGY A

A — Hosted AI voice calling agent

Build the smallest useful product: an inbound hotel or customer-support agent that answers real questions, performs safe tool calls, and transfers to a human when uncertain. Avoid owning the inference runtime.

GOALS

What v1 must do

  • Browser microphone conversation with interruption handling
  • Inbound telephone connection through an approved provider
  • Go-based tool execution with allowlisted endpoints
  • Room or appointment lookups with authoritative prices
  • Booking confirmation before any mutation
  • Call log, summary, status, optional recording consent
  • Human escalation on request, failure, or uncertainty
NON-GOALS

Do not build yet

  • Your own RTP packet scheduler or media SFU
  • GPU inference or fine-tuning infrastructure
  • Multi-tenant prepaid billing
  • Autonomous mass outbound marketing dialer
  • A second, incompatible agent orchestration framework
Go role

Implement the tool gateway, authentication, webhook verification, event handling and durable call ledger in Go. Use managed media or a proven SIP bridge.

Runtime contract

Agent runtime
Provider-specific integration with GPT-Live API or Realtime API. LiveKit Agents is an alternative orchestrator when you want provider-agnostic media and SIP routing; do not assume every combination works without an adapter.
Gateway service
Go 1.x (supported release), net/http or Chi, signed callbacks, token/session generation, tool middleware, request deadlines.
Persistence
PostgreSQL calls, call_events, tool_invocations, bookings; Redis for ephemeral session/cache and rate limits.
UX
Next.js admin console; static HTML/JS works for a proof of concept. Browser credentials must be short-lived and server-minted.
Accept criteria
Agent can converse, check availability, ask for explicit confirmation, place one test booking, and correctly escalate to a human. Every mutation is traceable.

Implementation steps

01
Browser-only realtime demo

Implement microphone permissions, secure server-minted session credentials, realtime event lifecycle, reconnect messaging, and transcript display.

02
Go tool gateway

Create read-only check_availability, get_quote, and get_policy APIs. Validate input, authorization and tool timeouts; never let model-supplied SQL execute.

03
Booking and escalation

Implement reserve_room with human confirmation, idempotency keys, quote expiry and transaction boundary. Provide a call-transfer fallback.

04
Telephony integration and testing

Configure inbound SIP/phone provider, audio format conversion as required, signed webhooks, recording disclosure, failed call handling, live call dashboard.

06 / STRATEGY B

B — Fully self-hosted open-source agent

Run audio recognition, language inference and speech output on owned hardware or rented GPUs. Choose between a modular pipeline and an experimental end-to-end duplex model after benchmarking quality on real phone audio.

PIPELINE 1

Chained STT → LLM → TTS

Recommended first self-hosted implementation for clear control over tools and language substitutions. Potential components: Silero VAD, faster-whisper or another streaming ASR, vLLM-served instruction model, and a streaming TTS engine.

Tradeoff: requires explicit endpointing, barge-in cancellation, audio buffering and cross-model scheduling.

PIPELINE 2

Native full-duplex speech

Research models such as Moshi maintain simultaneous audio streams. Qwen3-Omni is a distinct multimodal speech model family. Neither should be assumed to deliver the exact product capabilities, tool contracts or latency of ChatGPT Voice.

Tradeoff: more complex inference, adaptation and speech-language coverage. Check specific model licenses.

!
Hindi support is not automatic

For an India-focused calling agent, validate Hindi, Hinglish, regional accents, telephony noise and number pronunciation with your exact ASR/TTS checkpoints. Qwen3-Omni's published original speech-language list does not include Hindi audio output. Model capability claims must be checked per release.

Self-hosted engineering requirements

Audio correctness

  • RTP/Opus/PCM transcoding and validated sample rates
  • Timestamp-aligned audio queues
  • Echo suppression strategy and jitter handling
  • Pause detection and false-interruption recovery

Inference operations

  • GPU memory budget per loaded model
  • Warm starts and queue admission control
  • Cancellation propagated across ASR, LLM and TTS
  • Model quality, multilingual and licensing evaluation

Go vs Python vs Rust boundary

Go should handle sessions, routing, auth, scheduling and telemetry. Keep inference engines in their native runtimes — Python/CUDA for common model servers, Rust where a particular runtime provides stable high-performance codecs. Expose gRPC or bounded WebSocket interfaces; avoid moving tensor inference into Go just for stack purity.

07 / STRATEGY C

C — Voice AI infrastructure platform

This is a product for developers and businesses building their own calling agents. The differentiator must be more than an API wrapper: it needs reliability, tenancy, billing, routing, lifecycle management, integrations and a credible developer experience.

CONTROL PLANE

Tenant & agent management

Organizations, roles, API keys, phone number assignments, versioned prompts, voice profiles, agents, secrets and policy presets.

REALTIME DATA PLANE

Low-latency dispatch

Regional SIP and WebRTC ingestion, call session routing, media workers, model adapters, call transfer and backpressure.

BUSINESS PLANE

Usage and commerce

Per-call and per-tenant metering, costs, billing ledger, quotas, abuse monitoring, SLOs, export and support tooling.

Billing events must be idempotent and reconstructable from immutable call/session events.

Minimum useful platform

  • Two or more fully isolated tenants
  • Hosted-provider adapter with swap capability
  • Agent configuration/version deployment
  • Inbound and outbound call APIs
  • Webhook signing, retries and dead-letter events
  • Usage ledger, quota enforcement and invoices
  • Role-based access and tenant audit export

Anti-goals at launch

  • Implementing a new WebRTC SFU instead of using LiveKit
  • Operating dozens of model families from day one
  • Supporting all telephony providers without test certification
  • Promise of perfect multilingual or emotion recognition
  • Unlimited concurrent calls with no capacity controls
  • Building a proprietary model before proving demand

The moat must be workflow reliability, vertical specialization, deployment guarantees or economics — not merely exposing speech models behind an endpoint.

Suggested service decomposition

Go: tenant authentication, rate limiting, request schemas, API keys, audit correlation.
control-plane
Go: agent versions, telephony resources, configuration, policy enforcement, quotas.
call-dispatcher
Go: job routing, available media/agent worker selection, capacity admission, failover.
media-plane
LiveKit server + SIP bridge (both Go-based projects), unless a proven limitation justifies custom Pion media.
agent-runtime

metering

web-console
Next.js: organizations, numbers, agents, deployments, active calls, transcripts, usage and keys.

10 / HARDWARE & UNIT ECONOMICS

Size for latency, not just model memory

CPU-side audio scheduling, network quality, active session duration, token throughput, GPU batching and TTS generation can all saturate independently. These hardware figures are starting hypotheses; capacity must be load-tested with the actual models and call patterns.

A / HOSTED

4 vCPU · 8 GB

Development/pilot VPS for Go API, Postgres/Redis and light orchestration. No GPU if all AI inference/media are managed. Not a guaranteed call-concurrency target.

B / LOCAL LAB

64 GB + 24 GB VRAM

Practical starting point for modular local inference research. Specific duplex and multimodal checkpoints may need substantially more GPU memory.

C / PRODUCTION

Autoscaled pools

Dedicated Go control/media workers and optional provider or GPU inference pools. Scale on concurrent sessions, frame lag, CPU, p95 latency, GPU utilization and queue delay.

Capacity evaluation method

01
Record a representative test set

Include 100+ consented or synthetic dialogue scenarios: silence, barge-in, accents, Hindi-English code switching, noisy phone audio, long turns, and tool failures.

02
Load test by concurrent conversations

Increment sessions, not just requests per second. Capture jitter, speech start latency, token throughput, calls dropped, tool timeouts and GPU allocation.

03
Find the first saturated resource

Observe CPU media handlers, memory, bandwidth, provider rate limits, TTS queues, STT streams and model KV cache. Scale the bottleneck, not every service.

12 / RELIABILITY & TRUST

The requirements that decide if it ships

Realtime quality metrics

  • Time from caller speech end to first audible agent response
  • p50, p95, p99 round-trip turn latency per provider
  • Network jitter, packet loss and audio underruns
  • Interrupted vs false-interrupted response rate
  • Tool success, timeout and hallucinated-action rate
  • Human escalation and task-completion rate

Security and compliance

  • Disclose use of AI to callers when required/appropriate
  • Consent and lawful basis for recording and transcription
  • Opt-in, DNC checks and lawful outbound calling rules
  • Encrypt media/transcripts and restrict retention periods
  • Signed webhooks; RBAC and tenant-bound tool auth
  • Rate limits, PII redaction, emergency/human handoff

Security red lines

The agent may propose actions, but only the server authorizes them. No unrestricted shell or SQL tool, no implicit permission to transfer money or place orders, no voice-cloning of a real person without rights/consent, and no undisclosed or unlawful automated bulk calling.

13 / DELIVERY PLAN

Build the system in defensible increments

These are milestones, not guaranteed calendar estimates. Each stage has a measurable acceptance gate and is useful even if subsequent stages are never built.

M0 · FOUNDATION
One browser conversation

Hosted realtime model, microphone, event logging, reliable disconnect and human-readable logs.

M1 · PRODUCT A
One real workflow

Go tool gateway, room lookup, confirm/reserve flow, negative tests, human escalation.

M2 · TELEPHONY
One real phone number

Approved SIP/phone provider, inbound calls, signed webhooks, recordings policy and QA tests.

M3 · RESEARCH B
Local inference benchmark

Compare modular ASR/LLM/TTS with native duplex candidate under identical audio scenarios.

M4 · VALIDATE C
Two paying tenants

Only after demand: tenant isolation, metering, versioned agents, billing and horizontal worker pools.

Acceptance gates

A / EXIT CRITERIA

Business outcome proved

20+ varied scripted call scenarios pass; real caller can get correct answer or handoff; booking never duplicates. Provider bill is measurable.

B / EXIT CRITERIA

Latency and quality proved

GPU inference demonstrated with production-shaped call traffic, cancellation handling, accents, p95, dropout metrics and repeatable load tests.

C / EXIT CRITERIA

Multi-tenancy proved

Two independent tenants with isolated data/API keys, accurate usage ledgers, bounded quotas, complete webhook delivery and reproducible rollback.

15 / ARCHITECTURE REVIEW

Challenge the assumptions

The expensive mistakes are rarely a missing library. They are incorrect assumptions about reliability, latency, customer willingness to pay and the necessity of owning infrastructure.

DEVIL'S ADVOCATE

Assumption: ChatGPT-like speech requires a self-hosted full-duplex model. Counterpoint: Most business calls succeed with a well-tested modular system; measure interruption quality before overengineering.

PRAGMATIST

Assumption: Go should run every component. Counterpoint: Go is excellent for call control and media infrastructure; Python/Rust/CUDA may be better suited to inference runtimes. Use explicit process boundaries.

FINANCIAL ANALYST

Assumption: Owning a GPU is cheaper. Counterpoint: Underutilization, engineering overhead, on-call, model updates, and redundancy may dwarf per-minute hosted fees.

SKEPTICAL CUSTOMER

Assumption: Human-sounding calls are the value. Counterpoint: Customers pay for solved issues, correct reservations, short handling time and safe escalation.

ETHICS / COMPLIANCE

Assumption: Any available phone number can be dialed by an autonomous agent. Counterpoint: Consent, telemarketing restrictions, truthful AI disclosure, recording and data retention may determine whether the product is lawful.
